# 04 · 技术方案待定项

> ⚠️ 本文档记录**尚未拍板**的技术决策。进入编码前必须逐项确认。
> 特别约束：选型需重点评估「**降低 AI 生成代码幻觉风险**」——即优先选择训练语料充足、生态成熟、约定俗成的技术，避免 AI 在冷门框架上编造不存在的 API。

## 待定项清单

### 1. 后端语言与框架

**候选方向**（仅列出，未拍板）：

| 方向 | 幻觉风险考量 | 其他考量 |
|---|---|---|
| Node.js + Express/NestJS | 语料极多，AI 非常熟悉 | 与前端同语言，团队心智负担小 |
| Python + FastAPI/Django | 语料极多，文档规范 | 部署、并发模型需评估 |
| PHP + Laravel | 传统建站语料多 | 与微信生态的老教程契合度高 |

**讨论要点**：部署环境（服务器系统）、运维能力、与微信支付官方 SDK 的匹配度。

### 2. 前端方案

- 纯服务端渲染多页（简单、AI 幻觉风险低）？
- 还是轻量 SPA（Vue/React）？
- 移动端 UI 组件库选型（Vant / WeUI 等）

**倾向**：页面数量少（首页、表单、支付结果、我的订单），倾向简单方案。

### 3. 数据库

- MySQL / PostgreSQL / SQLite 起步？
- 订单、表单提交、图片记录三张核心表的设计

### 4. 文件上传（参考图）存储方案

- 服务器本地磁盘 + 定期备份？
- 对象存储（OSS / COS）？
- 成本与备案域名的配合

### 5. 部署方案

- 服务器：已有还是新购？在哪家云？
- HTTPS 证书（微信支付强制要求）
- 部署方式：手动 / Docker / 面板（如宝塔）

### 6. 防 AI 幻觉的工程策略（硬性要求，需专项讨论）

初步思路，待展开：

- **选型从众**：只用主流、长期稳定的技术栈，AI 语料覆盖充分
- **官方 SDK 优先**：微信支付用官方 SDK，不用第三方封装（避免 AI 编造不存在的封装方法）
- **小步生成 + 立即运行验证**：每次生成小模块，跑通再继续，不让 AI 一次性生成大段代码
- **以官方文档为锚**：关键 API 调用（支付、OAuth、模板消息）先贴官方文档原文给 AI，再让它写
- **类型与测试护栏**：用类型检查 + 关键路径自动化测试兜底，幻觉代码会在编译/测试期暴露
- **版本锁定**：依赖版本全部锁定，避免 AI 混用不同版本的 API

- 还是一期先用导出表格/数据库直查的方式？
